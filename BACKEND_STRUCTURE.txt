================================================================================
                    QUERY WIZARD — BACKEND STRUCTURE & PROCESS
================================================================================

This document explains how the Query Wizard backend is organized and how each
part works, from user login to SQL generation and execution.

--------------------------------------------------------------------------------
1. OVERVIEW
--------------------------------------------------------------------------------

The backend is a Flask API that:
  • Authenticates users via MySQL credentials (stored in .env).
  • Loads and caches the database schema (tables, columns, primary/foreign keys).
  • Converts natural language to SQL using Google Gemini AI.
  • Executes SQL against the user's MySQL database and returns results.
  • Can fix failed SQL and explain queries in multiple languages.

The React frontend (or Streamlit main.py) talks to this API. All database
credentials and schema are managed on the backend; the frontend only sends
prompts and receives SQL/results.

--------------------------------------------------------------------------------
2. FILES IN THE BACKEND
--------------------------------------------------------------------------------

  app.py            Entry point. Flask app, CORS, and all API routes.
  db_config.py      Loads .env and exposes DB_CONFIG; updates credentials on login.
  schema_handler.py Reads/writes mysql_schema.json; fetches schema from MySQL.
  db_handler.py      Executes SQL (execute_query_api for API, execute_query for Streamlit).
  query_parser.py   Fixes INSERT queries using schema (column order, placeholders).
  ai_generator.py   Translates prompts, calls Gemini for SQL generation/fix/explanation.
  prompt.py         Optional/longer prompt templates (not imported by app by default).
  mysql_schema.json Generated by schema_handler; stores table/column/FK structure.

--------------------------------------------------------------------------------
3. MODULE ROLES
--------------------------------------------------------------------------------

3.1  db_config.py
     • Loads .env from project root (parent of backend/).
     • Exposes DB_CONFIG = { host, user, password, database }.
     • update_env_credentials(db_name, db_password): writes DB_NAME and DB_PASSWORD
       to .env and refreshes DB_CONFIG so all modules use new credentials.
     • refresh_db_config(): reloads .env and updates DB_CONFIG in memory.

3.2  schema_handler.py
     • load_schema(): returns the schema dict from mysql_schema.json, or {} if missing.
     • save_schema(schema): writes the schema dict to mysql_schema.json.
     • get_table_columns(table_name): returns { column_name: { type, primary_key, foreign_key } } for one table.
     • store_all_table_structures(force_update=False):
         - Connects to MySQL using DB_CONFIG.
         - Runs SHOW TABLES, then for each table: DESCRIBE, SHOW KEYS (PRIMARY),
           and information_schema.KEY_COLUMN_USAGE for foreign keys.
         - Builds a dict: table_name -> { column_name -> { type, primary_key, foreign_key } }.
         - foreign_key is stored as "ReferencedTable(referenced_column)" or None.
         - Saves to mysql_schema.json. If force_update=True, always refetches; otherwise
           skips if file already exists.

3.3  db_handler.py
     • execute_query_api(query): used by the Flask API. No Streamlit.
         - Splits query by ";" and runs each statement.
         - INSERT: uses query_parser.fix_insert_query to get correct columns and values, then executemany.
         - DELETE/UPDATE/other DDL: execute + commit.
         - SELECT/SHOW/DESCRIBE: execute, fetch rows, return list of dicts (column -> value).
         - Returns (success: bool, error_message: str | None, results: list | None).
     • execute_query(query): same logic but for Streamlit (uses st.session_state, st.error, etc.).
     • extract_table_name(query): regex to get table name from FROM/INTO/UPDATE/JOIN for INSERT fix.

3.4  query_parser.py
     • fix_insert_query(query, table_name):
         - Gets column list for table_name from schema_handler.get_table_columns.
         - Parses VALUES (...), (...) from the query; normalizes values.
         - If first tuple is column names, treats it as header and removes it.
         - Builds parameterized INSERT with correct column order and %s placeholders.
         - Returns (corrected_query, values_list) or (None, error_message).

3.5  ai_generator.py
     • translate_to_english(text): uses deep_translator GoogleTranslator so prompts
       in any language are converted to English before sending to Gemini.
     • SQL_PROMPT: system prompt telling Gemini to output valid MySQL, use schema,
       handle foreign keys and full-database structure, LIMIT 100, etc.
     • _build_referenced_by(schema): builds reverse FK map — for each table, which
       other tables/columns reference it (e.g. "departments" is referenced by "employees.dept_id").
     • get_gemini_response(prompt, default_table=None):
         1. store_all_table_structures(force_update=True) and load_schema().
         2. Translate prompt to English.
         3. Optionally add default_table hint if no table name is mentioned.
         4. Build context: all tables and columns, "Table Relationships" (FK links),
            "Referenced by" (reverse FKs). Appended to the user prompt.
         5. Call Gemini with SQL_PROMPT + enriched prompt; strip markdown/code fences from response.
         6. Return the generated SQL string (or "AI Error: ..." on exception).
     • fix_sql_query(failed_sql, error_message, original_prompt=None, default_table=None):
         Same schema/relationship context as above; uses FIX_SQL_PROMPT so Gemini
         outputs a corrected query only.
     • get_sql_explanation(sql_query, target_language="en"): Gemini explains the
       query in English, then deep_translator translates to target_language if not "en".

3.6  app.py (Flask)
     • CORS allowed for frontend origins (e.g. localhost:5173).
     • has_db_credentials(): True if DB_PASSWORD and DB_NAME are non-empty (used as "auth").
     • Routes:
         POST /api/login          -> update_env_credentials(db_name, db_password); returns { success } or 4xx/5xx.
         GET  /api/check-auth     -> returns { authenticated: has_db_credentials() }.
         GET  /api/schema         -> load_schema(); if empty, store_all_table_structures(force_update=True) then load; returns { schema, tables }.
         POST /api/generate-sql   -> body: { prompt, default_table }; get_gemini_response(); returns { sql }.
         POST /api/execute        -> body: { sql }; execute_query_api(sql); returns { success, error, results }.
         POST /api/fix-sql        -> body: { failed_sql, error_message, original_prompt, default_table }; fix_sql_query(); returns { sql }.
         POST /api/explanation    -> body: { sql, language }; get_sql_explanation(); returns { explanation }.
     All routes except login and check-auth require has_db_credentials() (401 if not).

--------------------------------------------------------------------------------
4. REQUEST FLOW (HOW THINGS WORK END-TO-END)
--------------------------------------------------------------------------------

4.1  Login
      Frontend sends POST /api/login with { db_name, db_password }.
      -> app.login() calls db_config.update_env_credentials(db_name, db_password).
      -> .env is updated and DB_CONFIG refreshed so subsequent schema/execute use new DB.

4.2  Load schema (e.g. sidebar tables list)
      Frontend sends GET /api/schema.
      -> app.get_schema() checks auth, then load_schema(). If empty, calls
         schema_handler.store_all_table_structures(force_update=True) then load_schema() again.
      -> Returns { schema, tables } for the UI.

4.3  Generate SQL
      Frontend sends POST /api/generate-sql with { prompt, default_table }.
      -> app.generate_sql() calls ai_generator.get_gemini_response(prompt, default_table).
      -> ai_generator: refreshes schema from MySQL, translates prompt, builds full
         schema + relationships + "referenced by" context, calls Gemini, returns SQL.
      -> Response: { sql }.

4.4  Execute SQL
      Frontend sends POST /api/execute with { sql }.
      -> app.execute() calls db_handler.execute_query_api(sql).
      -> db_handler: connects with DB_CONFIG, splits statements; for INSERT uses
         query_parser.fix_insert_query; runs each statement, returns last SELECT-style
         results as list of dicts.
      -> Response: { success, error, results }.

4.5  Fix failed SQL
      Frontend sends POST /api/fix-sql with { failed_sql, error_message, original_prompt, default_table }.
      -> app.fix_sql() calls ai_generator.fix_sql_query(...).
      -> Same schema/relationship context as generate; Gemini returns corrected SQL only.
      -> Response: { sql }.

4.6  Get explanation
      Frontend sends POST /api/explanation with { sql, language }.
      -> app.explanation() calls ai_generator.get_sql_explanation(sql, language).
      -> Gemini explains in English; if language != "en", translate to that language.
      -> Response: { explanation }.

--------------------------------------------------------------------------------
5. DATA FLOW SUMMARY
--------------------------------------------------------------------------------

  .env (project root)
    -> db_config.load_dotenv + DB_CONFIG
    -> Used by: schema_handler (MySQL connection), db_handler (MySQL connection).

  MySQL (user's database)
    -> schema_handler.store_all_table_structures() reads tables, columns, PKs, FKs.
    -> schema_handler.save_schema() writes -> mysql_schema.json.
    -> schema_handler.load_schema() reads <- mysql_schema.json.
    -> ai_generator uses schema + relationships for Gemini context.
    -> query_parser uses get_table_columns() for INSERT fix.
    -> db_handler.execute_query_api() runs the final SQL.

  User prompt (natural language)
    -> ai_generator.translate_to_english()
    -> ai_generator.get_gemini_response() with schema + relationships
    -> Gemini API -> raw SQL string
    -> Frontend displays it; user can execute via /api/execute.

--------------------------------------------------------------------------------
6. DEPENDENCIES (conceptual)
--------------------------------------------------------------------------------

  app.py          -> db_config, schema_handler, db_handler, ai_generator
  schema_handler  -> db_config
  db_handler      -> db_config, schema_handler, query_parser
  query_parser    -> schema_handler
  ai_generator    -> db_config (for env), schema_handler, google.generativeai, deep_translator

--------------------------------------------------------------------------------
7. ENVIRONMENT VARIABLES
--------------------------------------------------------------------------------

  DB_HOST       MySQL host (default localhost).
  DB_USER       MySQL user (default root).
  DB_PASSWORD   Set by user at login; required for "authenticated" state.
  DB_NAME       Set by user at login; required for "authenticated" state.
  GOOGLE_API_KEY Required for Gemini (SQL generation, fix, explanation). Loaded from .env at project root.
